This notebook demonstrates how to put a LiteLLM Router in front of ZeroGPU to run an inbound lead desk: every "Contact sales" form submission is qualified, mined for structured fields, and answered with a first-touch reply. Each step runs on the smallest ZeroGPU model that can do the job, enterprise deals escalate to a frontier model, and every call lands in a cost ledger priced against a GPT-4.1 baseline. By combining LiteLLM and ZeroGPU, this notebook walks you through a practical pattern for routing high-volume, well-defined LLM work to cheap models while keeping a frontier model exactly where it earns its price.

For the full reference, see the [LiteLLM integration guide](/integrations/litellm).

In this notebook, you'll explore:

- **LiteLLM**: An open-source AI gateway that puts more than a hundred model providers behind one OpenAI-format interface. Here its Router groups deployments by pipeline step, retries and falls back between them, and reports the cost of every call from its built-in model cost map, including ZeroGPU's native `zerogpu/` route.
- **ZeroGPU**: A compute-efficient inference provider for apps and agents. We run purpose-built small and nano language models across an edge network for the high-volume tasks you run constantly - classification, extraction, moderation, routing, summarization - at ~10x lower latency and 50%+ lower cost than frontier-model workflows. Auto-scaling, with zero GPU infrastructure to manage. Plug in and you're live.
- **OpenAI**: A leading provider of advanced AI models capable of natural language understanding, contextual reasoning, and content generation. It enables intelligent, human-like interactions and supports a wide range of applications across various domains.

This setup not only demonstrates a practical application of tiered model routing for sales operations, but also provides a flexible framework that can be adapted to other real-world scenarios requiring cost-aware, multi-step LLM pipelines with structured outputs and a frontier-model safety net.

## 🧭 Building the Lead Desk Router

_Each step of the pipeline gets its own Router model group, backed by the cheapest ZeroGPU model that can do that step well, with GPT-4.1 as both the escalation target and the safety net._

```python Python
import json
from litellm import Router

# Drop params a model doesn't support (e.g. reasoning_effort on GPT-4.1) instead of raising
litellm.drop_params = True

ZEROGPU_HEADERS = {"x-project-id": os.environ["ZEROGPU_PROJECT_ID"]}
```

Now define the model groups. `qualify` runs on a fast 8B model, `extract` on `gpt-6-luna` for strict JSON, `draft` on the reasoning model `gpt-oss-120b`, and `frontier` on GPT-4.1:

```python Python
router = Router(
    model_list=[
        {
            "model_name": "qualify",
            "litellm_params": {
                "model": "zerogpu/llama-3.1-8b-instruct-fast",
                "extra_headers": ZEROGPU_HEADERS,
            },
        },
        {
            "model_name": "extract",
            "litellm_params": {
                "model": "zerogpu/gpt-6-luna",
                "extra_headers": ZEROGPU_HEADERS,
            },
        },
        {
            "model_name": "draft",
            "litellm_params": {
                "model": "zerogpu/gpt-oss-120b",
                "extra_headers": ZEROGPU_HEADERS,
            },
        },
        {
            "model_name": "frontier",
            "litellm_params": {"model": "openai/gpt-4.1"},
        },
    ],
    # If a ZeroGPU step fails after retries, the frontier model picks it up
    fallbacks=[
        {"qualify": ["frontier"]},
        {"extract": ["frontier"]},
        {"draft": ["frontier"]},
    ],
    num_retries=2,
)
```

Before running anything, check that LiteLLM knows what each ZeroGPU model can do. Strict `json_schema` output is the backbone of the first two steps:

## 🧾 Tracking Spend with a Cost Ledger

_Every Router call goes through one helper that records which model actually answered, the tokens it used, what it cost, and what the same tokens would have cost on GPT-4.1._

```python Python
ledger = []

def call(step, lead_id, model_group, messages, **kwargs):
    response = router.completion(model=model_group, messages=messages, **kwargs)

    cost = response._hidden_params.get("response_cost")
    if cost is None:
        cost = litellm.completion_cost(completion_response=response)

    # Price the identical tokens at GPT-4.1 rates from LiteLLM's cost map
    p_cost, c_cost = litellm.cost_per_token(
        model="gpt-4.1",
        prompt_tokens=response.usage.prompt_tokens,
        completion_tokens=response.usage.completion_tokens,
    )

    ledger.append({
        "lead": lead_id,
        "step": step,
        "model": response.model,
        "in": response.usage.prompt_tokens,
        "out": response.usage.completion_tokens,
        "cost": cost,
        "baseline": p_cost + c_cost,
    })
    return response
```

## 🎯 Step 1: Qualify Every Lead

_The `qualify` group reads each lead and returns three enums under a strict schema, so the code branches on fields rather than parsing prose._

```python Python
QUALIFY_SCHEMA = {
    "type": "json_schema",
    "json_schema": {
        "name": "lead_qualification",
        "strict": True,
        "schema": {
            "type": "object",
            "properties": {
                "intent": {"type": "string", "enum": ["sales", "support", "partnership", "spam"]},
                "segment": {"type": "string", "enum": ["enterprise", "mid_market", "smb", "unknown"]},
                "priority": {"type": "string", "enum": ["hot", "warm", "cold"]},
            },
            "required": ["intent", "segment", "priority"],
            "additionalProperties": False,
        },
    },
}

QUALIFY_PROMPT = (
    "You qualify inbound B2B leads. Segment by company size: enterprise is 1,000+ employees, "
    "mid_market is 100-999, smb is under 100. Priority is hot when budget or a near-term "
    "timeline is stated, warm when they are evaluating, cold otherwise. Spam and support are always cold."
)

def qualify(lead):
    response = call(
        "qualify", lead["id"], "qualify",
        messages=[
            {"role": "system", "content": QUALIFY_PROMPT},
            {"role": "user", "content": lead["text"]},
        ],
        response_format=QUALIFY_SCHEMA,
        temperature=0,
    )
    return json.loads(response.choices[0].message.content)

for lead in leads:
    lead["qualification"] = qualify(lead)
    print(lead["id"], lead["qualification"])
```

## 🔎 Step 2: Extract the CRM Fields

_For leads worth pursuing, the `extract` group pulls out the fields a CRM record needs. Nullable types let the model say "not stated" instead of guessing._

            "properties": {
                "name": {"type": ["string", "null"]},
                "company": {"type": ["string", "null"]},
                "role": {"type": ["string", "null"]},

}

## ✉️ Step 3: Draft the First-Touch Reply

_The reply step is where routing judgment pays off: a hot enterprise deal is worth frontier tokens, while everything else drafts perfectly well on ZeroGPU._

```python Python
DRAFT_PROMPT = (
    "You are an SDR. Write a warm, specific first-touch email reply under 110 words. "
    "Reference what the lead asked for, propose one concrete next step, and sign off as 'Sam, Acme Sales'. "
    "Return only the email body."
)

def pick_drafter(lead):
    q = lead["qualification"]
    return "frontier" if q["segment"] == "enterprise" and q["priority"] == "hot" else "draft"

def draft(lead):
    group = pick_drafter(lead)
    response = call(
        "draft", lead["id"], group,
        messages=[
            {"role": "system", "content": DRAFT_PROMPT},
            {"role": "user", "content": f"Lead message:\n{lead['text']}\n\nCRM fields:\n{json.dumps(lead['fields'])}"},
        ],
        reasoning_effort="low",  # used by gpt-oss-120b, dropped for GPT-4.1
        max_tokens=600,
    )
    return group, response.choices[0].message.content

for lead in pursue:
    group, lead["reply"] = draft(lead)
    print(f"--- {lead['id']} via {group} ---\n{lead['reply']}\n")
```

## 🛡️ Testing the Safety Net

_Fallbacks only matter if they work when ZeroGPU, the network, or a deployment has a bad minute. LiteLLM can simulate a failure so you can prove the path end to end._

Pass `mock_testing_fallbacks=True` and the Router fails the primary deployment on purpose, then walks the `fallbacks` list:

```python Python
response = router.completion(
    model="draft",
    messages=[
        {"role": "system", "content": DRAFT_PROMPT},
        {"role": "user", "content": f"Lead message:\n{leads[1]['text']}"},
    ],
    reasoning_effort="low",
    mock_testing_fallbacks=True,
)

print(f"requested group: draft")
print(f"answered by:     {response.model}")
print(f"cost:            ${response._hidden_params['response_cost']:.7f}")
```

```
requested group: draft
answered by:     gpt-4.1-2025-04-14
cost:            $0.0014320
```

The reply still went out, `reasoning_effort` was quietly dropped for GPT-4.1 thanks to `litellm.drop_params`, and the higher cost shows up in the same place as every other call, so a spike in fallback traffic is visible the moment it starts.
